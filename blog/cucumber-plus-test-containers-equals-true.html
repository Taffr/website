Cucumber + Test Containers == true

Intro

Span of tests, regressions, verifying behaviour, and drawbacks

The dream of a well tested system; one that catches regressions, one that is easy to extend, one which inspires confidence in refactors, and whose tests are never flaky is to many just that, a dream. It might seem so far away from reality that it is not even worth trying, or one might think that even starting to attempt to maintain such tests is a sisyphean, cursed to always push that boulder sized testing system, just for one flaky test to roll it back down the hill again.

In contrast, writing unit tests seems trivial (given that you have a way of mocking away any nasty side effects from dependencies0), but for many applications without complicated operations or business logic, unit tests seem to not test more than "given the data exists, then I get the data", which seems trivial and like a waste of time, which I can sympathize with. Unit tests can also many times miss the large picture, everything works fine in isolation, but when a dependency changes which was mocked in other services, we can sometimes encounter a blind spot that is not spotted, and we end up with a regression. No, ideally in such cases we would want to pair our unit tests with broader tests such as end-to-end tests.

End-to-end tests can be difficult to maintain, from my experience they are prone to "flakyness" ("A timeout here will surely fix this request sometimes taking a long time!"), and depending on your choice of testing (such as browser automation) can take a long time to develop. They also take quite a long time to run, making any effort to do TDD-like development feel a real chore.

However, if we narrow our focus just a little bit, and disregard testing the presentation and workflows, and instead focus on the actions and consequent effects that our users perform when interacting with our system, we can achieve many of the desired qualities of systems with end-to-end tests, but we can avoid almost all of the drawbacks of end-to-end testing.

Enter Cucumber

"Cucumber is a tool for running automated acceptance tests, written in plain language. Because they're written in plain language, they can be read by anyone on your team, improving communication, collaboration and trust."
That is a direct quote from Cucumber's own website, and if you are not already sold from that concept alone, I would argue that communication is not necessarily the biggest benefit, at least not to the average developer.

As they themselves describe, Cucumber lets you write test in plain language, this is done by following the Gherkin grammar. In essence that consists of writing expressions starting with either "Given", "When", or "Then". Each expression that starts with one of these keywords are called steps, and we group our steps into scenarios, and our scenarios into features. Features then describe all of the expected behaviour of our system we are testing.

As a simple example we have the following feature containing two scenarios 

  Feature: Authentication
    Scenario: Resource is denied when unauthenticated
      When I access a protected resource
      Then I am denied

    Scenario: Resource is allowed when authenticated
      Given I am logged in
      When I access a protected resource
      Then I am allowed access

These steps are then directly matched to one so called step-definition, which you are to implement in the language your project is using, and should act on the system under test in a manner that a user would, be it performing a HTTP request or similar. The steps are implemented exactly once, so they are easy to re-use between scenarios.

But as I mentioned, the execution of tests in plain text that anyone can read I would argue is not the main benefit of Cucumber1, rather I would list the main benefits as:

  • Regression in behaviour is easily spotted and remedied
    • Instead of reading through where a test case might have broken, we instead focus on if the behaviour has changed.
  • Tests are relatively fast to execute
    • Execution of a singular scenario is fast enough to run to iterate as you would when running unit tests.2, compared to running a traditional end-to-end test with for example browser automation.
  • They model actual user flows
    • Compared to carefully setting up a state which you then execute on steps are so composable and model actual actions to the system that it is easier to re-use them than to write a new complex setup for each new test.
    • Since the steps are so re-usable, the more actions and flows you model, the easier it becomes to write new ones.
  • Doing "test first"3 development at the behaviour level is easier than at unit test level.
    • Since we often go into a problem with a set of behaviours, probably described to us by a product person we more easily start writing one or more scenarios as the first thing we do, since we might not even have an idea of how we implement the behaviour as we start writing code, but we know what the behaviour should be. We can then keep the scenario(s) while we iterate on the solution.
